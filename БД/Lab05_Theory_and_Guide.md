# Лабораторная работа № 5 — Oracle Database
**Исследование архитектуры сервера: оперативная память и процессы**  
Среда: **Arch Linux + Docker + Oracle Database + SQL Developer**.

## 1. Как выполнять работу

1. Убедись, что контейнер работает: `docker ps` на Arch Linux.
2. Подключись к своей **PDB** в SQL Developer под пользователем, который может создавать таблицы и просматривать динамические представления `V$...` (права могут потребовать DBA). **Не создавай лабораторные таблицы под SYS или в CDB$ROOT.**
3. Открой `Lab05_Oracle_SQLDeveloper.sql`, выбери подключение и нажми **F5 / Run Script**. Так исполнятся все запросы, `PROMPT` и PL/SQL-блоки. Для отдельного запроса — `Ctrl+Enter`.
4. Если пункт 7 сообщает `KEEP отключён`, см. раздел «KEEP-пул». После включения KEEP повтори SQL-файл в **PDB**.
5. Выполни задания 17–20 из терминала Arch: `bash Lab05_Docker_Listener.sh ИМЯ_КОНТЕЙНЕРА`.
6. Для отчёта приложи результаты SELECT-запросов и вывод терминала (`lsnrctl status`, `lsnrctl services`, содержимое `listener.ora`, если файл существует).

### Контейнерные базы Oracle: CDB и PDB
- **Инстанс Oracle** = общая память (SGA и др.) + фоновые процессы; обслуживает CDB и открытые PDB. Поэтому `V$SGA*`, `V$PROCESS` отражают **инстанс**, а не отдельную «память одной PDB».
- **CDB$ROOT** — корневой контейнер базы; здесь меняют параметры памяти уровня инстанса.
- **PDB** — подключаемая БД; здесь удобнее создавать пользовательские таблицы `LAB05_KEEP`, `LAB05_DEFAULT`.
- Узнать контекст: `SELECT SYS_CONTEXT('USERENV','CON_NAME') FROM DUAL;`.
- Названия сервисов и пароли не универсальны: зависят от Docker-образа и способа его запуска.

### Если нет прав на системные представления
Запросы к `V$SGA`, `V$PROCESS`, `V$SESSION`, `V$BGPROCESS`, `V$SERVICES`, `V$PARAMETER` и другим представлениям могут требовать каталожных прав. Попроси DBA выдать **минимально необходимые SELECT на V_$...** либо используй администраторское подключение только для чтения. Для учебной БД также может использоваться `SELECT_CATALOG_ROLE`, но доступ определяется конкретной конфигурацией. DDL-часть лучше исполнять отдельной пользовательской схемой с `CREATE TABLE` и квотой на tablespace.

### Если KEEP = 0
По умолчанию `DB_KEEP_CACHE_SIZE = 0`; соответствующий пул не выделен. Параметр **не меняется из PDB**. DBA, находясь в `CDB$ROOT`, может выполнить, например:

```sql
-- Только административное подключение к корневому контейнеру CDB$ROOT:
SELECT SYS_CONTEXT('USERENV','CON_NAME') AS con_name FROM dual;
SELECT name, display_value, ispdb_modifiable
FROM v$parameter
WHERE name = 'db_keep_cache_size';

-- Пример для локальной учебной базы: размер подбирать по доступной SGA.
ALTER SYSTEM SET DB_KEEP_CACHE_SIZE = 64M SCOPE=MEMORY;
```

Размер 64M — **пример, не универсальная рекомендация**: Oracle может округлить размер или отказать при нехватке свободной SGA. Динамическое изменение может быть недоступно при конкретной конфигурации памяти. Изменение `SCOPE=MEMORY` не сохраняется в SPFILE и, как правило, не переживает перезапуск. После успешного изменения запусти SQL-файл **в PDB** повторно. Если нет DBA-привилегий, в пункте 7 корректно фиксируй, что пул выключен, и объясняй причину.

## 2. Теоретические вопросы — ответы для защиты

### 1. Расшифруйте аббревиатуру SGA
**System Global Area** — системная глобальная область, общая память инстанса Oracle. Используется серверными и фоновыми процессами для кэша блоков данных, разобранных SQL-команд, метаданных, записи redo и прочей инфраструктуры. **PGA** — отдельная, как правило не разделяемая память процесса, в отличие от SGA.

### 2. Основные пулы SGA и их назначение
- **Database Buffer Cache** — кэш блоков таблиц и индексов (подпулы DEFAULT/KEEP/RECYCLE и буферные кэши иных размеров блоков).
- **Shared Pool** — кэш разобранного SQL и PL/SQL (*library cache*), словарь данных (*data dictionary cache*) и другие общие структуры.
- **Large Pool** — выделения памяти для параллельных операций, shared server, некоторых операций резервного копирования/RMAN и т.п.; позволяет не занимать Shared Pool крупными выделениями.
- **Java Pool** — память для Java-компонентов внутри Oracle, если они используются.
- **Streams Pool** — память для соответствующих механизмов передачи/обработки данных, если включены.
- **Redo Log Buffer** — буфер записей повторного выполнения (redo), периодически записывается **LGWR** в online redo logs.
- **Fixed SGA** — фиксированные служебные структуры и управляющая информация. Не является настраиваемым пулом, подобным Shared Pool.

Не каждый компонент обязательно выделен. Посмотреть: `V$SGA_DYNAMIC_COMPONENTS`, `V$SGAINFO`.

### 3. Что такое SGA_MAX_SIZE и SGA_TARGET?
**SGA_MAX_SIZE** — верхняя граница, предусмотренная для SGA при запуске инстанса. Обычно для увеличения её значения требуется перезапуск. **SGA_TARGET** — целевой размер SGA при автоматическом управлении компонентами (ASMM); Oracle может менять размеры динамических пулов внутри выделенного бюджета. При использовании AMM / Unified Memory поведение определяется также параметрами более высокого уровня (`MEMORY_TARGET`, `MEMORY_SIZE` в поддерживающих версиях). Их не следует путать с уже выделенным размером, который показывает `V$SGA`.

### 4. Назначение буферного кэша
Хранит копии дисковых блоков таблиц/индексов в оперативной памяти, уменьшая физические чтения. Изменённые **dirty**-блоки записываются в файлы данных фоновым **DBWn**; redo по транзакциям пишет **LGWR**. Кэш не является отдельной постоянной копией БД и может очищаться/вытесняться.

### 5. DEFAULT, KEEP, RECYCLE
**DEFAULT** — обычный кэш для большинства объектов. **KEEP** — обособленный пул для часто читаемых объектов, которым полезно выделить устойчивую долю кэша. **RECYCLE** — обособленный, обычно небольшой пул для объектов, не заслуживающих долгого хранения в памяти. Важно: **KEEP не делает pin / вечное закрепление блока**, а использует обычные механизмы вытеснения внутри собственного пула. Назначение: `STORAGE (BUFFER_POOL KEEP)` либо `... DEFAULT/RECYCLE`. Существование отдельного пула зависит от параметров `DB_KEEP_CACHE_SIZE`, `DB_RECYCLE_CACHE_SIZE`.

### 6. Как работает LRU при вытеснении блоков?
**Least Recently Used** в базовой модели: редко используемые блоки становятся кандидатами на замену, часто используемые остаются ближе к горячей части списка. Реальная реализация Oracle сложнее простого «самый старый запрос» — учитывает характер обращений, hot/cold-сегменты, поведение full table scan и другие оптимизации. Если нет свободного буфера, подбирается кандидат; dirty-блок нельзя просто потерять, его при необходимости сначала записывают.

### 7. Как вытесняются блоки таблицы с CREATE TABLE ... CACHE?
Атрибут `CACHE` влияет на приоритет кэширования блоков при *full table scan* (противопоставляется `NOCACHE`). **Не гарантирует немедленную загрузку всей таблицы** в SGA и **не закрепляет блоки** навечно. Кэшируемые таким образом блоки продолжают вытесняться обычным алгоритмом кэша, когда требуются буферы для других данных. `CACHE` **не означает** `BUFFER_POOL KEEP`.

### 8. Как изменить размеры пулов?
Параметрами инстанса, обычно с `ALTER SYSTEM SET` (при наличии DBA-привилегий и в подходящем контейнере):

```sql
-- Только примеры, НЕ исполнять без проверки доступной SGA:
ALTER SYSTEM SET SGA_TARGET = 1G SCOPE=MEMORY;
ALTER SYSTEM SET DB_CACHE_SIZE = 256M SCOPE=MEMORY;
ALTER SYSTEM SET SHARED_POOL_SIZE = 256M SCOPE=MEMORY;
ALTER SYSTEM SET LARGE_POOL_SIZE = 64M SCOPE=MEMORY;
ALTER SYSTEM SET DB_KEEP_CACHE_SIZE = 64M SCOPE=MEMORY;
ALTER SYSTEM SET DB_RECYCLE_CACHE_SIZE = 64M SCOPE=MEMORY;
```

Эти размеры не нужно выставлять все сразу — суммарно они могут не поместиться. При **ASMM** некоторые значения задают минимумы компонентов, а Oracle динамически перераспределяет память. **В PDB доступны изменения только параметров с `ISPDB_MODIFIABLE = TRUE`**. Проверка: `V$PARAMETER` или `V$SYSTEM_PARAMETER`.

### 9. Какие пулы допускают изменение размера?
Динамические компоненты SGA, например **buffer cache, shared pool, large pool, Java pool, Streams pool**, а также отдельные буферные пулы при поддерживаемой конфигурации. Изменение ограничено гранулами, настройками автоматической памяти и доступными ресурсами. **Fixed SGA** и **Redo Log Buffer** нельзя независимо и произвольно менять в runtime как обычные динамические пулы; `LOG_BUFFER` задаётся при конфигурировании инстанса. `SGA_MAX_SIZE` также обычно требует перезапуска для изменения.

### 10. Для чего нужен LISTENER?
Это отдельный сетевой процесс Oracle Net (`tnslsnr` в Linux), принимающий подключения к заданному хосту/порту, сопоставляющий **SERVICE_NAME** с доступным экземпляром/обработчиком и передающий или организующий дальнейшее обслуживание клиента. Он **не выполняет SQL-запросы**. После установления dedicated-соединения работу с клиентом выполняет серверный процесс; listener не является универсальным посредником для каждого SQL-запроса.

### 11. Для чего нужен lsnrctl?
Утилита **Listener Control** для просмотра и управления Listener. Главные команды: `status` (состояние, адреса и сервисы), `services` (подробные сервисы, инстансы и обработчики), `help` (подсказка), `start`, `stop`, `reload` (управление). На лабораторной достаточно безопасных `status` и `services`; **не выключай Listener во время работы других подключений**.

### 12. Что такое сервис?
**Database Service** — логическое имя/точка доступа, по которой клиент подключается к определённой БД/PDB или группе экземпляров. Сервис отделяет клиентское подключение от физического SID. В SQL Developer обычно задают `Hostname`, `Port`, `Service name`. Просмотр: `V$SERVICES`; фактически зарегистрированные у конкретного listener: `lsnrctl services`.

### 13. Какие сервисы создаются автоматически?
Обычно **сервис по имени/глобальному имени базы**, а в многоконтейнерной архитектуре — **сервис для PDB** при создании/открытии PDB. Внутренние сервисы `SYS$USERS`, `SYS$BACKGROUND` также могут встречаться в служебных представлениях, но не являются обычными внешними пользовательскими адресами подключения. Фактические имена (например `FREEPDB1` или `XEPDB1`) зависят от образа и настройки, поэтому их **нужно смотреть в своей системе**, а не угадывать.

### 14. Dedicated vs Shared Server
**Dedicated:** отдельный серверный процесс обрабатывает запросы конкретного клиентского соединения; просто и удобно, но при тысячах одновременных сессий расходует больше процессов/памяти. **Shared:** соединение обслуживается через **dispatcher (Dnnn)**, а запросы выполняет общий пул **shared server (Snnn)**; один серверный процесс может обслуживать разные сессии по очереди, что снижает издержки при большом числе преимущественно неактивных подключений. Для shared надо настроить параметры `DISPATCHERS`, `SHARED_SERVERS` и связанные ограничения. Проверка: `V$SESSION.SERVER`, `V$DISPATCHER`, `V$PARAMETER`.

### 15. Для чего нужен LISTENER.ORA?
Файл конфигурации Oracle Net Listener: задаёт адреса, протоколы, порты и дополнительные параметры. При необходимости содержит **статическую** регистрацию экземпляров (`SID_LIST_LISTENER`). При обычной динамической регистрации **LREG** сообщает сервисы Listener без ручного перечисления их в `listener.ora`; в некоторых Docker-образах отдельного файла может не быть. Пример структуры (это **не содержимое твоего реального файла**):

```text
LISTENER =
  (DESCRIPTION_LIST =
    (DESCRIPTION =
      (ADDRESS = (PROTOCOL = TCP)(HOST = 0.0.0.0)(PORT = 1521))
    )
  )
```

В Docker ещё есть **проброс порта** на хост (`docker ps`); порт на Arch может отличаться от внутреннего 1521.

### 16. Основные фоновые процессы
- **DBWn** — пишет dirty-блоки buffer cache в файлы данных.
- **LGWR** — пишет redo из Redo Log Buffer в online redo log, важен для фиксации транзакций.
- **CKPT** — сигнализирует о checkpoint и обновляет сведения о контрольной точке в заголовках файлов/контрольном файле; сам массовой записью блоков не занимается.
- **SMON** — системное обслуживание и восстановление после сбоя инстанса.
- **PMON** — отслеживает/очищает последствия завершения процессов и сессий; конкретные обязанности менялись между версиями.
- **LREG** — динамически регистрирует сервисы/экземпляры у Listener.
- **ARCn** — архивирует заполненные online redo logs, если настроен ARCHIVELOG.
- **MMON/MMNL** — сбор статистики и обслуживание механизмов мониторинга.
- **MMAN** — управление перераспределением памяти (где применимо).

Другие фоновые процессы зависят от версии и конфигурации (например, RECO, CJQ0, VKTM и др.). Достоверный список: соединить `V$BGPROCESS` с работающими строками `V$PROCESS`.

### 17. Что такое серверный процесс? Как его просмотреть?
Это процесс Oracle, выполняющий работу по запросу клиента: разбор и исполнение SQL, чтения блоков, взаимодействие с SGA/PGA и пр. **Серверный процесс не то же самое, что фоновый процесс.** В SQL: `V$PROCESS` (процессы ОС/инстанса) + `V$SESSION` (привязка пользовательской сессии по `PADDR`); для простаивающих процессов режима Shared Server — `V$SHARED_SERVER`. Внутри Docker: `ps -ef`, `ps -p PID -f`. Важно: `V$PROCESS.SPID` — идентификатор ОС *в пространстве имён контейнера*, поэтому PID с Arch-хоста может отличаться.

## 3. Самые частые дополнительные вопросы / ловушки

**SGA и PGA — одно и то же?** Нет. SGA — общая память инстанса, PGA — приватная память отдельного процесса.

**Равен ли SGA_TARGET реально выделенному размеру SGA?** Не всегда: параметр — настройка/цель определённого механизма управления; измерять фактическое выделение удобнее через `V$SGA` и `V$SGAINFO`.

**Гранулы у всех пулов одинаковые?** Для динамических компонентов конкретного инстанса обычно используется одна единица распределения; `V$SGA_DYNAMIC_COMPONENTS.GRANULE_SIZE` показывает её на компонентах. Фиксированная SGA и redo buffer — исключения.

**«Свободная память SGA» и «free memory в large pool» совпадают?** Нет. Первая — свободный ресурс для перераспределения/расширения компонентов SGA; вторая — свободные выделения **внутри** уже существующего Large Pool.

**Если таблица создана в KEEP, значит все её строки всегда в RAM?** Нет. `BUFFER_POOL KEEP` задаёт, **куда** помещать считанные блоки, а не принудительное и бессрочное хранение всей таблицы в памяти.

**Если есть `CREATE TABLE ... CACHE`, то она в KEEP?** Нет. `CACHE` — атрибут политики кэширования при full scan; `STORAGE (BUFFER_POOL KEEP)` — выбор пула.

**Если в `V$SERVICES` есть сервис, почему его не видно в `lsnrctl services`?** Представление БД и список **зарегистрированных у конкретного listener** сервисов — разные источники. Проверяют LREG, доступность Listener, `LOCAL_LISTENER`; администратор может выполнить `ALTER SYSTEM REGISTER`.

**Если `listener.ora` отсутствует, Listener сломан?** Нет. Сервисы могут регистрироваться динамически, а Listener может работать с настройками по умолчанию.

**Где Windows-сервис на Arch?** Его нет. Linux-эквивалент в контейнере — процесс `tnslsnr`; жизненный цикл чаще управляется entrypoint Docker-образа, а не сервисом Windows или host-systemd.

**Можно запускать всё в SQL Developer?** SQL/PLSQL — да. `docker`, `ps`, `lsnrctl`, просмотр файлов — в терминале Arch или в shell контейнера. SQL*Plus необязателен, если SQL Developer уже подключён.

## 4. Команды на Arch для демонстрации

```bash
# Выполнить на хосте Arch Linux
docker ps
bash Lab05_Docker_Listener.sh ИМЯ_КОНТЕЙНЕРА

# Или исследовать вручную:
docker exec -it ИМЯ_КОНТЕЙНЕРА sh
# Внутри контейнера:
ps -ef | grep '[t]nslsnr'
lsnrctl status
lsnrctl services
# Для выхода из контейнера:
exit
```

`sqlplus` — дополнительный клиент в контейнере (если он установлен и настроена среда). Для лабораторной он **не обязателен**, потому что Oracle SQL Developer поддерживает исполняемые SQL/PLSQL-скрипты. Утилита **lsnrctl** — отдельная от SQL*Plus программа; её запускают из Linux-shell.
