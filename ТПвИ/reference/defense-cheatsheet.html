Лаба 1: NGINX

ВопросКороткий ответ
Что это?Событийный HTTP-сервер, сервер статики, reverse proxy и балансировщик.
Процессыmaster читает конфигурацию и управляет; workers обрабатывают соединения; cache loader/manager обслуживают кэш.
Forward proxyСтоит со стороны клиента, скрывает клиентов от внешнего сервера.
Reverse proxyСтоит со стороны серверов, принимает входящий запрос и выбирает backend.
Конфигурацияhttp → server → location; виртуальный сервер задаётся блоком server.
Статикаroot, index, try_files.
Проксиproxy_pass; обычно передаются Host, X-Real-IP, X-Forwarded-For.
Проверкаnginx -t, затем nginx -s reload или systemctl reload nginx.
Журналыaccess_log — запросы; error_log — диагностика.

Лаба 2: путь запроса

Kestrel→ RequestLoggingMiddleware→ Routing→ Controller→ ChannelRegistry→ Channel<string>

Важно: ответ проходит middleware в обратном направлении; поэтому оно может записать статус и тело ответа.

Объекты и роли

ОбъектРоль
ChannelRegistrySingleton-реестр каналов в ConcurrentDictionary; живёт всё время работы процесса.
ChannelEntityМетаданные канала, флаг ACTIVE/CLOSED и bounded FIFO-очередь строк.
Channel<string>Потокобезопасная producer/consumer очередь: Writer пишет, Reader читает.
DTOКонтракты JSON между клиентом и API; не отдают внутренний объект очереди.
ControllersПроверяют команду, выбирают действие и формируют HTTP-ответ.
MiddlewareПерехватывает все запросы и ответы для Trace/Debug.

Очередь и статусы

  • enqueue → WriteAsync; при свободном месте возвращает 200.
  • Ёмкость равна 1, режим Wait; второй producer ждёт освобождения места.
  • Через 3 секунды linked cancellation token отменяет ожидание → Warning + HTTP 408.
  • peek смотрит элемент, dequeue извлекает; на пустой очереди оба дают 200 с data: null.
  • Неизвестный GUID → Error + 404; CLOSED-канал → Warning + 409.

Logging

Событие создаётся кодом один раз, затем проходит независимую фильтрацию для каждого провайдера. Провайдер определяет, куда вывести запись; категория и уровень — пропускать ли её.

УровеньСмысл в проекте
TraceВход в методы, параметры, краткая трассировка запроса/ответа.
DebugПолные заголовки и тела HTTP-запроса/ответа.
InformationСтарт/остановка приложения, жизненный цикл каналов.
WarningПовторный open/close, CLOSED-канал, истечение WaitEnqueue.
ErrorНеуспех отдельной операции, например 404.
CriticalАвария приложения или инфраструктуры; в обычном сценарии не генерируется.

Правило порога: минимальный уровень включает себя и всё серьёзнее. Например, Warning пропускает Warning, Error, Critical, но не Information.

Куда попадают логи

  • Console: Warning+ для приложения; Error+ для Microsoft.
  • Debug: в Development — Debug+ для категорий ASPA0011_1....
  • Logfile: в Development — Trace+ для ASPA0011_1...; вне Development — Information+.
  • Microsoft в файл не попадает: для Logfile стоит Default=None, а разрешена только категория ASPA0011_1.

Демонстрация за 90 секунд

  1. Запустить проект в Development и открыть app.log.
  2. POST /api/channels с ACTIVE → 201 и GUID.
  3. PUT open того же GUID → 200, Warning в консоли и файле.
  4. Первый enqueue → 200; очередь заполнена.
  5. Второй enqueue → ожидание около 3 секунд, затем 408 и Warning.
  6. peek → тот же первый элемент остаётся; dequeue → тот же элемент удаляется.
  7. GET неизвестного GUID → 404 и Error.
  8. Показать в app.log номера событий, дату, категорию, Trace/Debug/Information/Warning/Error.

Ограничения, которые полезно признать

  • Всё хранится в памяти и исчезает после перезапуска.
  • ACTIVE/CLOSED — только логический флаг; writer не завершается, канал можно снова открыть.
  • data — строка с JSON внутри JSON, а не типизированный JSON-объект.
  • Файловый logger учебный: синхронно блокирует поток на записи и не делает ротацию.
  • Middleware буферизует полные тела и заголовки; в production так можно записать секреты и потратить много памяти.
