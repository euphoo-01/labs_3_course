От NGINX до очереди и логов в ASP.NET Core

Цель — не заучить строки кода, а удерживать одну модель: кто принимает запрос, кто маршрутизирует его, где живёт состояние и почему одна запись видна в файле, но не в консоли.

1. Общая картина двух работ

Клиент / Postman→ NGINX→ Kestrel + ASP.NET Core→ Controller→ Channel<string>

В первой работе изучается внешний вход в веб-систему: NGINX может отдать статический файл сам или передать динамический запрос backend-приложению. Во второй работе реализован сам backend. В текущем репозитории NGINX не подключён к приложению физически — связь концептуальная, по архитектуре веб-системы.

Не путать два значения слова «канал». В NGINX это не основной термин. В лабораторной 2 канал — объект с GUID, состоянием и очередью System.Threading.Channels.Channel<string>.

2. Теория первой лабораторной: NGINX

Что такое NGINX

NGINX — событийный HTTP-сервер. Он умеет обслуживать статические файлы, завершать TLS, работать reverse proxy, распределять запросы между несколькими backend-серверами и взаимодействовать с приложениями через HTTP, FastCGI, SCGI или uWSGI.

Forward proxy

Клиент сознательно отправляет трафик прокси. Внешний сервер видит адрес прокси, а не конечного клиента. Защищается или контролируется сторона клиентов.

Reverse proxy

Клиент обращается к публичному серверу и может не знать о backend. Прокси скрывает внутренние серверы, балансирует нагрузку и централизует TLS, кэш и журналы.

Почему NGINX выдерживает много соединений

Один master process читает конфигурацию, проверяет её и управляет рабочими процессами. Несколько worker processes фактически обрабатывают соединения. Worker использует неблокирующую событийную модель, поэтому ему не нужен отдельный поток на каждый ожидающий сетевой запрос. Cache loader загружает метаданные кэша при старте, cache manager следит за его размером и устареванием.

Конфигурационная иерархия

events { worker_connections 1024; }

http {
  server {
    listen 80;
    server_name example.test;

    location / {
      root /var/www/app;
      try_files $uri $uri/ /index.html;
    }

    location /api/ {
      proxy_pass http://127.0.0.1:5080;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
  }
}
  • http содержит настройки HTTP-подсистемы.
  • server описывает виртуальный сервер: адрес, порт и имя.
  • location выбирается по URI и определяет обработку части запросов.
  • root сопоставляет URI с каталогом; index задаёт стартовый файл.
  • try_files ... /index.html важен для SPA: неизвестный браузерный маршрут должен открыть React-приложение, а не дать 404.
  • proxy_pass передаёт запрос backend. Заголовки сохраняют имя хоста и реальный адрес клиента.

Типичные расположения: основной файл /etc/nginx/nginx.conf, дополнительные конфигурации — /etc/nginx/conf.d/*.conf; в Debian/Ubuntu часто есть sites-available и ссылки в sites-enabled.

nginx -t                 # проверить синтаксис и ссылки на файлы
nginx -s reload          # применить конфигурацию без жёсткой остановки
systemctl status nginx   # состояние сервиса
systemctl reload nginx   # reload через systemd
ps -ax | grep nginx      # увидеть master и workers
nproc                    # число доступных CPU

При reload master проверяет новую конфигурацию. Если она корректна, запускает новых workers, а старые перестают принимать новые соединения и заканчивают уже начатые. Это graceful reload.

Частая ошибка на защите: «NGINX запускает C#-код». Обычно нет. Для ASP.NET Core NGINX проксирует HTTP-запрос Kestrel. FastCGI типичнее для PHP, uWSGI — для соответствующего Python-стека.

3. Как собирается приложение в Program.cs

  1. CreateBuilder(args) создаёт host, DI-контейнер, конфигурацию и logging infrastructure.
  2. AddControllers() регистрирует MVC-контроллеры и model binding.
  3. Configure<AppOptions> связывает секцию App с типизированными настройками.
  4. AddSingleton<ChannelRegistry> создаёт один общий реестр на весь процесс.
  5. ClearProviders удаляет стандартный набор; затем явно добавляются Console, Debug и собственный File provider.
  6. Build() завершает конфигурацию приложения.
  7. UseMiddleware<RequestLoggingMiddleware> ставит перехватчик в конвейер.
  8. MapControllers() создаёт endpoints по атрибутам маршрутизации.
  9. ApplicationStarted/Stopping пишут Information о жизненном цикле.
  10. Run() запускает Kestrel и удерживает процесс.

DI сам передаёт ChannelRegistry и ILogger<T> в конструкторы контроллеров. Реестр singleton, а контроллер создаётся при обработке запроса; поэтому в логе видно повторяющееся событие ControllerCreated.

4. Где живут данные и почему выбран Channel

ChannelRegistry содержит ConcurrentDictionary<Guid, ChannelEntity>. Обычный Dictionary небезопасен при параллельных HTTP-запросах, а concurrent-коллекция поддерживает атомарные операции поиска, добавления и удаления.

Каждый ChannelEntity содержит GUID, имя, описание, логический флаг активности и Channel<string>. Очередь ограниченная: QueueCapacity=1, FullMode=Wait. Она работает по producer/consumer-модели и в данном сценарии сохраняет FIFO-порядок.

enqueue: Writer.WriteAsync→ bounded FIFO→ dequeue: Reader.TryRead

Когда единственное место занято, второй WriteAsync не блокирует поток синхронно, а асинхронно ждёт. Это backpressure: быстрый producer замедляется до скорости consumer. В лабораторной ожидание ограничено WaitEnqueue=3.

using var timeout = CancellationTokenSource
  .CreateLinkedTokenSource(requestAborted);
timeout.CancelAfter(TimeSpan.FromSeconds(3));
await channel.Queue.Writer.WriteAsync(data, timeout.Token);

Linked token объединяет две причины отмены: клиент разорвал HTTP-запрос или истёк таймер. Catch-фильтр превращает только внутренний тайм-аут в HTTP 408.

CLOSED не означает Complete. Код меняет только IsActive. Он не вызывает Queue.Writer.Complete(), поэтому накопленные данные остаются, а канал можно снова открыть.

5. Что происходит при HTTP-запросе

Пример: POST /api/queue, команда enqueue

  1. Kestrel принимает HTTP-запрос.
  2. Middleware читает и возвращает на начало тело запроса, пишет Trace и Debug.
  3. Маршрутизация выбирает QueueController.Execute.
  4. Model binding превращает JSON в QueueCommandRequest.
  5. Контроллер ищет GUID в singleton-реестре и проверяет ACTIVE.
  6. Enqueue проверяет data и вызывает WriteAsync с тайм-аутом.
  7. Результат превращается в IActionResult, затем JSON и HTTP-статус.
  8. На обратном пути middleware читает буфер ответа, логирует его и копирует клиенту.

6. Теория и практика Logging

Logging состоит из четырёх независимых понятий:

  • ILogger — API, через которое код создаёт событие.
  • Уровень — серьёзность: Trace, Debug, Information, Warning, Error, Critical.
  • Категория — источник события. У ILogger<QueueController> это полное имя класса.
  • Провайдер — получатель: Console, Debug, Logfile. Одно событие может уйти сразу в несколько.

Фильтр выбирается отдельно для пары «провайдер + категория». Значение уровня — минимальный порог. Information пропускает Information, Warning, Error и Critical; оно не включает Trace и Debug. В формулировке слайда лекции здесь легко оговориться.

ПровайдерОбычная конфигурацияDevelopment добавляет
ConsoleASPA: Warning+; Microsoft: Error+Ничего
DebugNoneASPA: Debug+
LogfileASPA: Information+; остальные NoneASPA: Trace+

[ProviderAlias("Logfile")] связывает имя секции Logging:Logfile с пользовательским провайдером. Фабрика логгеров отбрасывает запрещённые события до вызова FileLogger.Log.

Как устроен FileLogger

  • FileLoggerProvider.CreateLogger(categoryName) создаёт логгер для категории.
  • Log форматирует дату, EventId, уровень, категорию, имя события и сообщение.
  • Interlocked.Increment выдаёт уникальный номер события безопасно при конкуренции.
  • lock не позволяет нескольким запросам одновременно перемешать строки файла.
Учебная, не production-реализация. File.AppendAllText синхронно открывает/пишет файл на каждом событии, нет очереди, batch-записи и ротации. Middleware записывает тела и заголовки без маскировки секретов.

7. Проверенный сценарий демонстрации

Проект успешно собирается. На фактическом запуске получена следующая цепочка:

  1. ACTIVE-канал создан: 201 Created, сервер вернул GUID и заголовок Location.
  2. Повторный open: 200 OK, в консоли и файле появился Warning.
  3. Первый enqueue: 200 OK, единственное место занято.
  4. Второй enqueue: через 3.01 секунды вернулся 408 Request Timeout.
  5. peek вернул первый элемент, не удалив его.
  6. dequeue вернул тот же первый элемент и удалил его.
  7. GET неизвестного GUID: 404 Not Found, в консоли и файле появился Error.

В app.log подтверждены последовательные EventId, timestamp, категории и события всех уровней от Trace до Error. Для локального запуска на проверенной машине пришлось разрешить major roll-forward, потому что проект нацелен на .NET 8, а установлены runtime 9 и 10. На лабораторном компьютере с .NET 8 обычного dotnet run достаточно.

8. Вопросы защиты: сначала ответьте вслух

Не раскрывайте ответ, пока не сформулировали свой. Это важнее повторного чтения.

1. Чем reverse proxy отличается от forward proxy?

Forward proxy представляет клиентов перед внешними серверами; reverse proxy представляет внутренние серверы перед клиентами.

2. Что делают master и worker процессы NGINX?

Master читает и применяет конфигурацию и управляет workers. Workers в событийной модели обрабатывают сетевые соединения и HTTP-запросы.

3. Зачем сначала выполнять nginx -t?

Чтобы проверить синтаксис и доступность связанных файлов до reload и не пытаться применить ошибочную конфигурацию.

4. Почему ChannelRegistry зарегистрирован как Singleton?

Все HTTP-запросы должны видеть один общий набор созданных каналов. Новый registry на каждый запрос терял бы общую очередь.

5. Зачем ConcurrentDictionary, если Channel потокобезопасен?

Channel защищает операции своей очереди, но не коллекцию всех ChannelEntity. Реестр отдельно должен выдерживать параллельные добавления, поиски и удаления.

6. Почему второй enqueue не завершается сразу?

Bounded channel имеет capacity 1 и FullMode.Wait. После первого элемента producer получает backpressure и WriteAsync ждёт свободного места.

7. Чем peek отличается от dequeue?

TryPeek читает первый элемент без удаления; TryRead возвращает и удаляет его.

8. Что такое linked cancellation token?

Токен, который отменяется при любой из связанных причин: отмене HTTP-запроса клиентом или истечении внутреннего тайм-аута.

9. Уйдёт ли Information в Console при пороге Warning?

Нет. Порог Warning пропускает Warning, Error и Critical. Более подробные уровни отбрасываются.

10. Почему Microsoft Error не попадает в app.log?

Для провайдера Logfile Default=None, а разрешён префикс категории ASPA0011_1. Категория Microsoft под это правило не подходит.

11. Почему middleware возвращает Position тела запроса в 0?

После чтения поток находится в конце. EnableBuffering и сброс позиции позволяют model binding затем прочитать тот же JSON.

12. Что исчезнет после перезапуска?

Все ChannelEntity и сообщения, потому что registry и очереди находятся только в памяти процесса. Файл app.log останется.
